# Architecture Map

You are producing or refreshing a lightweight, durable map of a codebase's structure.

This map is deliberately low-resolution: structural orientation only, not a catalogue of every concept, business rule, or behaviour. It exists so that other skills — especially `feature-planner` — don't have to re-derive top-level structure from scratch on every run, which is expensive on large codebases. Feature- or task-specific investigation (tracing a particular behaviour, finding analogous code) stays with whichever skill needs it, since that depends on what's actually being worked on and won't stay accurate as a static artefact anyway.

## When to run

- Called by another skill that needs a fresh map for orientation and finds none, or finds one that's stale.
- Called directly when the user asks to map, document, or get oriented in a codebase.

## Workflow

1. Run `scripts/staleness_key.sh <repo-root>` to compute the current staleness key and (if applicable) the current git HEAD.
2. Check whether `ARCHITECTURE.md` exists at the repo root:
   - **Doesn't exist** → full generation (below).
   - **Exists, has recognized frontmatter** (a `staleness_key` field) → compare it to the freshly computed key.
     - Matches → fresh. Report this and stop; do not regenerate.
     - Differs → stale. Refresh it (targeted or full, below).
   - **Exists, but has no `staleness_key` frontmatter** → this file wasn't generated by this skill, most likely a human-authored doc. **Do not overwrite it.** Write the newly generated map to `ARCHITECTURE-generated.md` instead, and tell the user clearly that a pre-existing `ARCHITECTURE.md` was left untouched and the generated map was written alongside it under a different name.

### Full generation

Explore the repository at orientation depth only:

- top-level structure
- apps/packages and their boundaries
- frontend/backend/service boundaries
- major domains and roughly where they live
- test organisation and conventions
- build/package configuration
- existing developer/architecture docs worth pointing to

Do not trace specific business logic, concepts, or end-to-end flows here — leave that to whichever skill consumes the map.

Draft the top-level map using `templates/ARCHITECTURE.md`:
- The Mermaid diagram should show domain/service-level boundaries and dependencies only — roughly 10-20 nodes, not individual files or classes.
- Every path reference (domains, apps/packages, docs) goes in a markdown table under a column literally named `Path`, so it can be mechanically verified later.

**Apply the size budget.** Keep the top-level `ARCHITECTURE.md` under roughly 300 lines. If including a domain's full detail inline would push the file past that, split that domain out:
1. Write its detail to `.architecture/domains/<slug>.md` using `templates/domain-submap.md`.
2. In the top-level `Domains` table, keep only its one-line summary row, with the `Details` column linking to the sub-map file.

Not every domain needs a sub-map — only split out the ones whose detail doesn't fit the budget.

Fill in `staleness_key`, `generated_at_commit` (if git), and `generated_at` in the frontmatter of every file written (top-level and any sub-maps), using the values from step 1.

**Verify paths** before finishing: run
```
python3 scripts/verify_paths.py <repo-root> ARCHITECTURE.md .architecture/domains/*.md
```
against every file just written. Fix any reported `MISSING` paths (either the path is wrong, or the referenced code doesn't actually exist and the row should be corrected or removed) before reporting completion.

### Targeted refresh (preferred when stale, not missing)

When a map already exists but is stale:

1. If the top-level map's frontmatter has a `generated_at_commit` and the repo is a git repo, run `git diff --stat <generated_at_commit>..HEAD` plus `git status --porcelain` to see which paths changed since generation.
2. If the changes are confined to one or a few domains, re-explore and update only those domains — their entries in the top-level table, and their sub-map file if they have one. Leave everything else as-is.
3. If the changes are broad (touch most top-level areas), or there's no `generated_at_commit` to diff from (non-git fallback was used), do a full regeneration instead — targeted refresh isn't worth the bookkeeping at that point.
4. Update `staleness_key`, `generated_at_commit`, and `generated_at` in the frontmatter of every file touched (top-level always, since its own staleness key changed; sub-maps only if their content changed).
5. Re-run `scripts/verify_paths.py` (see above) against every file touched before finishing.

## Output

- Save the top-level map to `ARCHITECTURE.md` at the repository root (or `ARCHITECTURE-generated.md` if a non-conforming file already occupied that name — see step 2 above), and any sub-maps to `.architecture/domains/`.
- Report to the user (or the calling skill) whether this was a fresh-hit, a targeted refresh, or a full regeneration; which domains (if any) got their own sub-map; and a one-line summary of what the map covers.
- The map is a starting point, not ground truth. Anything load-bearing for the current task should be verified against the actual code — the staleness key catches file changes, not semantic drift in code that wasn't touched, and path verification only confirms paths exist, not that descriptions are accurate.
